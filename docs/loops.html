Thinking in loops · agentsa1-opencode-ralph

Six nested loops that teach a local model to code better

The whole project is one idea, repeated at six time scales: from a slow curriculum loop that runs for months, to the agentic loop of the model that in seconds edits a file. Each ring feeds the ring inside it — and learning happens in two places.

repo: koenvanwijk/agentsa1-opencode-ralph target: Agents-A1 → DeepSeek V4 Flash (backend swapped, alias) harness: OpenCode CLI without: fine-tuning any weights

The map

Loops within loops

Read from the outside in: each ring is a loop that spins the ring inside it many times before taking one step itself. Outer = slow and rare, inner = fast and constant. The core is the model that actually types.

  • Learning — kept change / growing curriculum
  • Evaluation — measures fitness (score)
  • Control — keeps the loop running, does not learn
  • Core — the model that actually edits files

Besides these 6 nested execution loops, three side/meta loops also hook in: the adaptive proposer (who writes the proposal), the fan-out (subagents with their own scoped AGENTS.md) and the DSL-builder loop (per-DSL learning from external plugins) — all three further down.

Inside L4 · the fitness function

Deterministic or not — two axes

Evaluation is not one thing. The ruler (the verifier) is deliberately deterministic; the generator (the model) is deliberately stochastic. So the loop runs each task 3× and takes a majority — turning a wobbly generator + a hard ruler into a stable signal together.

axis 1 The ruler — deterministic

Exact output diff: 17_bank_ledger, 18_txn_wal compare statement.txt/final.txt/… against a golden string — one byte off = fail.

pytest: 21_sgf_parsing restores the pristine test and runs pytest. Gate + DSL: 26_flag_cleanup checks dead flags are gone, all languages compile, the DSL via dslc.py.

Exception (opt-in, OFF by default): JUDGE=llm → judge.py scores the “subjective residue” with an LLM — non-deterministic, hence off: it keeps the loop fast and reproducible.

axis 2 The generator — non-deterministic

temperature 0.4: each trial samples differently, so the same task can be flaky (1/3, 2/3) or stable (0/3, 3/3). The loop's answer: TRIALS=3 + majority vote.

Temperature was deliberately raised (0.1 → 0.4) to break the deterministic “explore-then-stop” attractor on 17/18: at temp 0.1 the model lands every time on the same “read and stop” continuation; some entropy gives a few trials the “write solve.py” branch.

A meta loop · per DSL plugin

The DSL-builder loop — learning from external plugins

For each mini-DSL there is yet another propose-&-test loop, but at a different level: it is not the small model that learns here, but a capable builder model that distils from an external corpus (documentation + good examples) a linter + cheatsheet — tested before they may enter the loop. Crucially, the loop core stays generic and company-neutral; each DSL is a plugin in its own git repo, attached as a submodule. So company content (possibly IP-bound or R1/R2) never enters the loop repo.

The heart of your question

Where does learning happen?

No model weights change anywhere. “Learning” happens in five places, all outside the model — in the prompt, in the selection, in the curriculum, in memory, and in external corpora. And the prompt itself is no longer a single file: the steering is layered.

1 In-context — the main learning

Where: a layered steering surface, no longer a single file: (a) main oc_profile/AGENTS.md — injected every default turn; (b) per-subagent scoped AGENTS.md in the fan-out; (c) on-demand DSL cheatsheets grammars/<name>.md.

Hill-climbing in prompt space: “never stop after a Read”, exact SGF-parser recipes, hex-neighbour offsets — each distilled from an observed failure in a trajectory.

2 Selection pressure — the bar

Where: ralph.sh:136–149. The bar decides what stays: ratchets up on a win, EMA decay on a loss.

This way only a reproducible improvement survives; a lucky hit evaporates over a few rounds. This is the fitness/selection of the evolution.

3 Curriculum — escalation

Where: L1. As soon as all tasks pass, a harder task is added.

The system grows its own learning target so there is always something to gain — otherwise selection pressure would vanish and learning would stop.

4 Meta-memory — across runs

Where: RESULTS.md (the decision ledger) and the proposer that reads trajectories as a “gradient”.

What worked across experiments (temperature, subagents, the explore-only trap) is recorded and reused for the next proposal.

5 External plugin — per DSL

Where: a capable builder model distils a cheatsheet + linter per DSL from an external DSL plugin (its own git repo, submodule) — the only place where learning comes from outside, while the loop core stays generic and company-neutral.

Again a propose → test → keep/rollback loop, one level deeper and tested with dslc selftest. See the DSL-builder loop above. (deterministic half now implemented for the flags reference; LLM builder + submodule discovery not yet.)

The shortest summary → L4 measures, L2 selects, L1 raises the bar, and the result of all that learning lands in one place every time: the text in AGENTS.md that L6 — the model that actually types — re-reads every turn. The model itself stays unchanged; the harness around it gets smarter.
